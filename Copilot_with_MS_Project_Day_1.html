PARTICIPANT EDITION · DAY 1

Copilot with MS Project

Build a credible project plan, understand its scheduling logic and use AI to explore improvements you can explain and validate.

Your learning journey

Read Modules 1–4, use the searchable terminology reference, then open Participant Labs to practise in Project desktop.

What you will produce

A Namma OTT WBS and linked schedule, a migration variation, an SDLC plan, a sprint capacity decision and a reviewed AI scenario.

Keep the tools distinct. Project desktop calculates the .mpp schedule. Copilot proposes or explains using available evidence. Planner AI works in a separate cloud plan. There is no assumed automatic synchronisation with your local .mpp.

Before you begin

  • Project desktop installed and activated for the participant.
  • Excel for tables and import exercises. Licensed, authorised Copilot access for hands-on AI; otherwise complete the manual alternative.
  • Use fictional documents and profiles. Keep source files and scenario copies separate.

The guide covers Day 1 only. Detailed resource costing, EVM, baselines and progress reporting belong to Day 2 and are not developed here.

MODULE 1

Introduction to Copilot

A useful response starts with clear context and ends with human review.

Core AI terminology

Microsoft Copilot

An AI assistant across Microsoft products. Capabilities depend on the product, account, licence and permissions.

Prompt engineering

Designing, testing and refining instructions, context and output requirements to obtain useful responses.

GPT and LLM

GPT means Generative Pre-trained Transformer. A large language model learns language patterns and generates responses from context.

Tokens and context

Tokens are pieces of text processed by a model. Context is information available to it for the response.

Grounding

Anchoring a response in relevant supplied or retrieved evidence. Grounding improves relevance but cannot guarantee correctness.

RAG

Retrieval-Augmented Generation: retrieve relevant material and use it to support generation. Attaching a document does not permanently train the model.

Hallucination

A plausible but unsupported or incorrect output. Check source references and calculations.

Agent

An AI system that can use tools to pursue tasks within its configured capabilities and permissions. Confirm actual changes in the target application.

Activity: diagnose the basic prompts

Predict the missing information before expanding each answer.

Create a 6-month software development schedule.

Missing product scope, start date, calendars, dependencies and capacity. Dates may look approved despite having no evidence.

Generate milestones for a banking application.

Missing release scope, acceptance evidence, regulatory context and decision owners.

Identify project risks for cloud migration.

Missing architecture, migration waves and evidence. Separate future risks from existing issues.

Suggest resource allocations.

Missing skills, availability, calendars and other commitments. A role label does not create capacity.

Two ways to structure a prompt

CO-STAR

Context, Objective, Style, Tone, Audience, Response. This framework helps specify the situation and the communication you need.

A project scheduling checklist

Context + Goal + Inputs + Constraints + Output + Validation. Supply approved scope, resource availability, calendars and dependencies. Ask for traceable estimates and questions. This is a practical checklist, not the expansion of CO-STAR.

A stronger Namma OTT prompt

Act as a project planning assistant. Draft a six-month software delivery outline for the fictional Namma OTT pilot. Scope is user sign-in, a video catalogue and playback of licensed demo content. Exclude payments, production-scale DRM and recommendation engines. Use Monday to Friday working weeks. Include deliverables, work packages, suggested durations, predecessor references, role owners and acceptance criteria. Clearly label estimates and assumptions. Do not claim this is a calculated or approved schedule. Return a table and five questions for the sponsor.

Follow-up prompts

Identify missing deliverables and unsupported assumptions. Cite the requirement IDs. Revise only the affected rows and explain each change.

Review scope coverage, fabricated resources, unsupported dates and acceptance criteria. A confident response is not evidence of an accurate estimate.

MODULE 2

Building project plans

Organise what must be delivered before deciding how work will flow.

Terminology

Task

A scheduled activity with a defined outcome. Example: build the catalogue API.

Subtask

A task nested beneath a summary task. It has its own duration, links and assignments.

Summary task

A parent that rolls up its children. Its duration spans their dates, rather than adding all child durations.

WBS

Work Breakdown Structure: a hierarchical decomposition of project scope into manageable deliverables and work packages.

Work package

A manageable portion of scope that can be estimated, assigned and accepted. Its detail depends on project governance.

Indenting and outlining

Indent makes selected tasks children of the preceding parent; outdent moves them up. Collapsing changes the view, not the schedule.

Task hierarchy

Parent–child structure showing scope organisation. Hierarchy does not create execution dependencies.

Task ID and Unique ID

ID identifies the current row position and can change. Unique ID is a more stable task identifier within the file.

Outline number and WBS code

Outline Number shows position in the hierarchy, such as 1.2.1. A WBS code labels scope; it is not a predecessor link.

Milestone

A significant event or gate. Use 0d for the classroom example, with acceptance evidence such as signed UAT approval.

Constraint

A rule limiting when a task starts or finishes. Example: testing cannot start before an environment becomes available.

Deadline

A target date that can produce a warning when forecast completion is late. It normally leaves the schedule free to calculate.

Duration and work

Duration is working-time span. Work is effort across assignments. A three-day task at 100% for one person on an 8h day has 24h work.

From scope to a WBS

  1. Identify deliverables and exclusions from the approved scope.
  2. Break deliverables into manageable work packages and activities.
  3. Enter summary and leaf tasks in Project. Select child rows and choose Task → Indent Task.
  4. Add acceptance milestones using 0d. Put the required evidence in task notes.
  5. Insert Outline Number and inspect the hierarchy. Add dependencies between appropriate leaf tasks separately.
An Agile hierarchy varies by organisation. Value stream → theme → epic → feature → story → task is one possible organising convention. Epic ≤2 months and feature ≤1 month are workshop conventions, not universal Scrum rules. MVP means Minimum Viable Product, a learning-oriented product concept, not a delivery model.

Constraints versus deadlines

Double-click an auto-scheduled task → Task Information → Advanced. Choose Constraint Type and, when required, Constraint Date. Use a Deadline for a target you want to monitor while preserving a realistic calculated forecast.

MODULE 3

Dependencies and scheduling

The first word describes the predecessor event. The second describes the successor event.

Predecessor and successor

The predecessor controls a relationship; the successor depends on it. The predecessor is not always chronologically earlier, as SF illustrates.

Finish-to-Start (FS)

B cannot start until A finishes. Use: approved architecture before environment provisioning. Enter 5FS on B when A has ID 5.

Start-to-Start (SS)

B cannot start until A starts. Use: batch validation alongside migration. Enter 5SS. SS does not force identical start times.

Finish-to-Finish (FF)

B cannot finish until A finishes. Use: final reconciliation cannot finish before the final migration batch. Enter 5FF.

Start-to-Finish (SF)

B cannot finish until A starts. Use: temporary support coverage continues until incoming support starts. Enter 5SF on the outgoing coverage task.

Lag

A deliberate delay on a dependency. 5FS+2d starts B at least two working days after A finishes, subject to calendars and other scheduling rules.

Lead

Overlap represented by negative lag. 5FS-1d permits B to start one working day before A finishes. Confirm partial handover is feasible.

Critical Path Method (CPM)

Network analysis that calculates the chain controlling the project finish, using activity durations and dependencies.

Critical path

The currently finish-driving chain under the model. It can change when durations, calendars or constraints change.

Total slack or float

How much a task can slip without delaying project finish under the model. Slack is not spare staffing capacity.

Auto scheduling

Project calculates task dates from durations, links, calendars and other rules. Use it for the reference labs.

Manual scheduling

You control task dates and durations more directly. Missing or inconsistent values can remain; dependencies do not drive it like an auto-scheduled plan.

Fast tracking

Overlap work that was sequential. Potential duration saving comes with dependency and rework risks.

Crashing

Add or change qualified capacity to shorten suitable critical work. Added people do not guarantee proportional speed gains.

Working calendar

Defines working periods and exceptions. Hours/day is a conversion setting and does not by itself change calendar working time.

Deadline management

Compare calculated dates with commitments, investigate warnings and seek decisions instead of forcing tasks onto desired dates.

Entering links in Project

  1. Use Gantt Chart and Auto Scheduled tasks.
  2. Enter the predecessor ID and relationship in the successor’s Predecessors field, such as 5SS+2d. A bare ID defaults to FS.
  3. For several predecessors, use the Windows list separator, commonly comma or semicolon.
  4. Alternatively, open Task Information → Predecessors and set Type and Lag.
  5. Change one duration in a scenario copy. Inspect the finish, critical path and any constraint conflicts.

What each link controls

Sequential work · FS

Architecture approval finishes before provisioning starts. This is appropriate where the input must be complete.

Overlapping work · SS

Batch migration starts before validation of available batches starts. SS alone does not coordinate their finishes.

Completion control · FF

Final reconciliation cannot finish before the last migration batch finishes. FF alone does not establish a start boundary.

Handover · SF

Temporary support coverage cannot finish until incoming support starts. In a real cutover, an accepted operational-readiness milestone may better represent the handover.

Critical path reasoning

Project performs a forward/backward scheduling calculation over the dependency network. A change to a noncritical task may fit within slack, so project finish does not move. After a recovery change, another branch can become critical. Inspect critical-task settings and deadlines before interpreting red bars.

Mini check

Does an SS link guarantee two simultaneous starts?

No. It establishes a lower boundary; other links, calendars or constraints can push the successor later.

Does 2d always mean two calendar days?

No. Ordinary duration uses working time. Weekends and calendar exceptions affect the date span.

MODULE 4

AI-assisted scheduling

Draft alternatives with Copilot. Validate the resulting schedule in Project.

Draft

Generate timeline outlines and candidate milestones from reviewed scope and acceptance gates.

Challenge

Identify potential bottlenecks, missing logic and skill constraints. Supply evidence instead of asking for generic advice.

Compare

Explore parallel execution, component reuse, revised scope or additional qualified capacity. Record assumptions and risks.

Validate

Test a scenario in Project. Check calendars, links, work, capacity and quality consequences before approval.

An evidence-based six-month forecast

  1. Provide the approved requirement document, architecture, skills matrix, allocations, calendars and historical team delivery data.
  2. Ask Copilot to summarise its understanding, cite sources and identify gaps before scheduling.
  3. Review a prioritised backlog with acceptance criteria and Definition of Done.
  4. Draft detailed near-term work and coarser later release outcomes using two-week sprints. A six-month roadmap is a forecast.
  5. Review estimates with the team and validate the proposed work in Project.

Story points have no universal hours conversion. Planning Poker is the authentic technique name. Velocity is a team’s completed points per sprint using its own scale; do not assign “individual velocities” or compare teams by points.

The four workshop requests

Using only this schedule snapshot and the supplied calendars/capacity: optimise the schedule; propose how to reduce duration by 15%; identify bottlenecks; and suggest feasible parallel execution. For each proposal provide task IDs, current and proposed values, evidence, assumptions, risk and validation needed. Do not claim to have recalculated Project or edited the .mpp.

Export, review and update

Export selected fields through File → Export → Save Project as File → Excel Workbook. Keep Unique ID, hierarchy, Summary flag, links and calendar context. Ask Copilot to add proposal columns. Apply a small set of approved changes manually or test a carefully mapped merge import in a copy. Excel is a field snapshot, not a complete round-trip of the scheduling model.

Keep Desktop and Planner workflows separate. Use an available licensed Planner AI surface for in-plan tasks, and inspect the actual plan after each operation. A generic chat message saying “updated” does not prove a change. No shared cloud plan or automatic synchronisation is supplied by this HTML file.

Lab 6 · Agile sprint capacity decision

Use a two-week sprint, normally 10 working days. Define Done as implemented, reviewed and tested. Keep sprint boundaries explicit rather than assuming a summary forces the timebox.

Expected reasoning

80h demand exceeds 64h delivery capacity by 16h. One option is sign-in 24h + catalogue 24h + review/fixes 8h = 56h, leaving 8h contingency. Defer playback. This exercise uses hours, not story points.

Lab 7 · AI-assisted 15% optimisation

Use the clean 26-day Namma file, with no resources or levelling effects for this controlled comparison.

Review this fictional 26-working-day Namma OTT schedule. Propose a reduction of at least 15 percent while preserving scope and approval gates. Show changed task IDs and durations, prerequisites, staffing assumptions, risks and cost implications. Identify missing information. Do not claim to have recalculated Project or edited my file.
Expected result

Playback alone at 3d gives 25d. The combined scenario gives 22d, finishing 15 December 2026. (26 − 22) / 26 × 100 = 15.38%. Reuse, automation or qualified capacity must justify the shorter estimates; these are scenario assumptions, not proven savings.
